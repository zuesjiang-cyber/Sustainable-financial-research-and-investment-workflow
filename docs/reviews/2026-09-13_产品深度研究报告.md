## 1. 产品是什么：定位与价值主张

### 1.1 真实定位

仓库名是 `Sustainable-financial-research-and-investment-workflow`，但产品实际名为 **FinTrust**，定位是：

> 把一次性研报，变成会随财报进化的研究记忆。

**与仓库名不符**：全库检索 `ESG|sustainab|可持续|碳排放|carbon|绿色|气候|climate`，仅 4 处命中，且全部无关（2 处是 CSS 的"绿色"配色说明，2 处是"业务可持续性"的中文语义）。**产品与 ESG / 可持续金融零关联**。这会直接影响对外沟通、检索与融资叙事。

### 1.2 目标用户与真实痛点

来自 `docs/product-architecture-v1/01_产品定义与交互.md`：

- **用户**：已阅读公司研报、需要跟踪兑现情况的研究员、投资经理助理、高投入个人研究者。
- **痛点不是**"看不懂财报摘要"，**而是**：之前为什么看好这家公司？新财报改变了哪些判断？下次该盯什么？
- **现状成本**：在旧研报、最新财报、个人笔记之间反复往返。

**PM 评价**：痛点定义精准且真实。这是"研究过程资产化"问题，不是"信息获取"问题。定位在一个有付费意愿、但被通用 Chat 工具服务得很差的窄缝里。

### 1.3 核心价值主张（README 五条）

| 价值 | 代码是否兑现 |
|---|---|
| 观点有记忆（版本化 Markdown Memory） | ✅ 真实兑现 |
| 证据有来源（页码、坐标、原文片段） | ⚠️ **部分虚假**——页码真、原文真、**坐标是占位值**（见 §4.4） |
| 变化有解释（旧判断、新事实、差距、原因） | ✅ 结构兑现，质量未验证 |

| 用户有最终决定权 | ✅ 真实兑现 |

### 1.4 差异化：产品判断真正出色的地方

这是本项目最值得保护的部分。以下几点在同类"AI 投研"产品中普遍缺失：

**① 状态语义拒绝廉价乐观**

四态 `SUPPORTED / PARTIALLY_SUPPORTED / WEAKENED / UNRESOLVED`，并且把三件容易混淆的事**分成三个独立字段**：

- `status`：结论
- `maturity`：`NOT_DUE / IN_PROGRESS / DUE`（期限到了没有）
- `interimSignal`：`ABOVE / ON_TRACK / BELOW / UNKNOWN`（阶段节奏）

设计文档给的反例非常专业：

> 研报预测 2026 年收入同比 20%，一季报同比 8%。全年目标未到期，结果为 `UNRESOLVED / IN_PROGRESS`，阶段信号可以 `BELOW`；**不能说全年预测被证伪**。

代码真实实现了这一点（`src/server/agent/researchAgent.ts`，`maturityFor()` 与 IN_PROGRESS 分支）。**这是真正的金融领域理解，不是套壳。**

**② 数字归代码，语义归模型**

`src/server/facts/metricRegistry.ts` 用 Decimal.js 实现毛利率与同比，并在计算前强制四项可比性检查：`ENTITY_MATCH`、`PERIOD_MATCH`、`SCOPE_MATCH`、`NON_ZERO_DENOMINATOR`。任一不通过则 `result: null`，**不输出一个看起来合理的数字**。

同比计算中，上期为 0 或负数时返回 `POSITIVE_BASE: false` 而非硬算增长率——这正是"扭亏/减亏"不能被表达成常规增速的专业细节。

**③ 原因分四层，且拒绝把相关当因果**

`observedGap`（可观察差距）→ `disclosedCauses`（公司披露原因，带 `MANAGEMENT_EXPLANATION` 归因标记）→ `hypotheses`（系统假设，须列 `missingEvidence`）→ `nextQuestions`。

`researchAgent.ts` 的 `evidenceBackedExplanation()` 在找不到原因证据时，输出的是：

> "当前财报片段披露了用于核验的数值事实，但未明确披露该结果的经营原因。"

**而不是编一段行业套话。** 这是产品诚实度的硬编码保障。

**④ 证据门禁（evidence gating）**

`v1Router.ts` 的 `addSemanticReviews()`：

```ts
const hasSemanticEvidence = semanticEvidenceIds.length > 0;
const semanticStatus = item.status && hasSemanticEvidence ? item.status : "UNRESOLVED";
```

模型给了结论但没引用任何有效 span → 状态强制回落 `UNRESOLVED`，summary 不被模型改写。**这是防幻觉的真实机制，不是提示词里写一句"不要编造"。**

**⑤ Fail-closed 而非降级**

`requireLing()` 检查 provider 与 model 名必须精确等于 `inclusionai/ling-3.0-flash-fin:free`，否则 503。不回退 Gemini、不回退规则、不回退固定样例。（代价见 §4.6）

**⑥ Markdown 作为 Memory 载体**

`markdownMemoryStore.ts`：人可读正文 + 机器可解析 JSON 块，原子写（临时文件 + rename）。可直接 Git 备份、可人工审阅、可手工修复。对一个"个人研究资产"产品，这是正确的产品决策。

## 4. 具体产品缺陷（按严重度）

### 4.1 【严重】演示数据污染真实数据路径

**我实测复现了这个问题。** 运行 `npm test` 之后：

```bash
$ curl -s http://127.0.0.1:3000/v1/projects | jq
3 projects
  - 圣邦股份 300661 T0 | theses: 2
  - 圣邦股份 300661 T0 | theses: 1
  - 圣邦股份 300661 T0 | theses: 2
```

这些"真实项目"的 `thesisId` 是 `00000000-0000-4000-8000-000000000201`，文件 SHA 是 `2688dd70...`——**全部来自 `v1Router.ts` 里硬编码的 `DEMO_*` 常量**。它们指向一个不存在的 PDF（`圣邦股份深度研究报告.pdf`，`isSynthetic: true`）。

**三条根因**：

1. **测试不隔离 Memory 目录**。`tests/demo-pipeline.test.ts` 只设了 `FINTRUST_DATA_DIR` 和 `FINTRUST_UPLOAD_STORAGE_DIR`，但 `MarkdownMemoryStore` 默认写 `process.env.FINTRUST_MEMORY_DIR || ./research-memory` —— **未隔离**。我实测跑完测试后 `research-memory/` 出现 4 个 `.md` 文件。

2. **测试直接写 Git 跟踪的数据库**。`V1Store` 默认 `getDataDir()` → `./data`，而 `data/fintrust.sqlite` **被 Git 跟踪**（`.gitignore` 只忽略 `data-local/`）。`git status` 实测显示 `M data/fintrust.sqlite`、`M tests/fixtures/output_manifest.json`（测试重写跟踪的 fixture）、`M project/**/__pycache__/*.pyc`（`.pyc` 被跟踪）。

   > **跑一次测试就脏一次工作区。** CI 不可信，本地开发体验受损。

3. **demo run 可以被 confirm 成真实项目**。`v1Router.ts:668` 的 `getRunOrDemo()` 让 `run-demo-t0` 可被读取，随后 `POST /v1/runs/run-demo-t0/draft/confirm` 走的是**与真实项目完全相同的落库路径**（`memoryStore.saveProject` + `store.saveProject`），且不写 `isSynthetic` 标记。

**这直接违反项目自己的规则**。`CHATGPT_WORK_HANDOFF.md`：

> 固定圣邦/汇顶内容只能作为明确标识的 Demo，**不能进入真实上传路径**。

**用户可见影响**：首页"继续已有真实研究项目"会列出这些假项目；点进去是一个引用不存在 PDF 的空壳研究，且**永久留在 Markdown Memory 里**。对一个以"Memory 是可信长期资产"为核心卖点的产品，这是自我否定。

### 4.2 【严重】财报核验是同步 HTTP 请求，必然超时

`POST /v1/projects/:id/filing-runs` 在**一个 HTTP 请求内同步完成**：

```
读项目 → 取全部 active theses → 逐条 researchAgent.assessThesis()
→ 读取财报全部 spans → 排序打分 → 截断到 40 条 / 18,000 字符
→ 一次 Ling 模型调用（max_tokens 默认 24,000）
→ Zod 校验 → 落 Fact → buildCalculations → DiffGenerator → 存 run → 返回
```

没有 job、没有 checkpoint、没有 SSE、没有超时保护（`FINTRUST_MODEL_TIMEOUT_MS=45000` 只在 `completeWithResearchModelTimeout` 里生效，而这条路径**没有使用它**——直接 `await modelTransport.complete(...)`）。

**后果**：一份 200 页年报 → 解析（Python 子进程，无超时）+ 一次 24k token 的模型调用，全部阻塞在一个请求里。浏览器、Express、任何反向代理都会先超时。

**设计文档明确要求异步**（`03_端到端工作流与状态机.md`：202 + job + SSE + checkpoint + lease；P0-10"刷新、关闭页面或 Worker 重启不丢任务"）。`jobs/queue.ts`（186 行）和 `jobs/worker.ts`（94 行）**已经写了，但是死代码**。

> 这是当前**最大的可用性天花板**，也是把已写好的队列接线就能解决的高性价比项。

### 4.3 【严重】真实两轮验收从未绿过

见 §2.2。产品自己在 `12_验收与评测.md` 定义了完成标准：

> 操作者上传一份此前未跑过的真实研报 PDF……随后输入下一期财报，再更新一次：同一观点 ID 保留、先前修正生效、旧问题被处理、v1/v2 可回看。

以及量化目标：关键观点召回 ≥85%、可用观点精确率 ≥90%、**已使用数字事实准确率 ≥95%**、原文定位正确率 **100%**、核验结论可接受率 ≥85%、核心高风险误判 **0 个**、第二轮连续性 100%。

**实测状态：以上指标没有任何一项被测量过。** `14_资料准备清单.md` 要求的 `demo-materials/` 目录不存在。

### 4.4 【高】"证据有来源"名不副实：坐标是假的

`python/document_parser/parser.py:118-126`，**所有文本块的 bbox 是硬编码常量**：

```python
blocks.append({
    "id": b_id, "type": b_type, "headingPath": [],   # ← headingPath 恒为空

        "pageNumber": page_num,

表格单元格（`:88-96`）：每个 cell 的 `bbox` 都等于**整张表的 `norm_tbl_bbox`**，不是单元格位置。

> 诚实评价：`17_MVP完整Walkthrough.md` 确实声明了"原文引用和原页查看在本 MVP 中不展示"。**取舍本身是合理的**——问题在于 README 和 `parser-manifest` 契约仍在承诺坐标，而坐标是伪造值而非"未实现"。应当要么补真，要么显式标注为不可用。

### 4.6 【中】问题只增不结，违反自己的设计原则

`v1Router.ts` 的 `mergeQuestions()`：把新问题 append 到旧问题列表，按 `thesisId:text` 去重。

### 4.7 【中】前端"补充观点"凭空造出无出处的假观点

`ThesisReviewView.tsx` 的 `handleAddThesis()` 硬编码：

```

服务端 `normaliseThesisInput` 接受它（`sourceEvidenceIds` 为空 → `allowedEvidenceIds` 检查通过），`normaliseCriterion` 默认 `origin: "USER_CONFIRMED"`。

**后果**：一条**没有任何研报出处**、带着捏造目标值（`net_profit ≥ 20`）的观点，被写进 T0，成为长期跟踪基线。

`ThesisReviewView.tsx` 提供三个选项：

用户可以在 T0 把观点口径设为"分部"，之后**每次上传财报都会失败**，且报错位置在财报上传而非口径选择处。典型的"UI 承诺 > 后端能力"。

### 4.9 【中】财报期间与口径完全依赖用户手填，无交叉校验

`UploadFilingModal` 要求用户自行选择 `reportType`（Q1/HALF_YEAR/Q3/ANNUAL）、填 `period.start/end`、`basis`（QUARTER/YTD/YEAR）、`publishedAt`、`scope`。

## 5. 商业与需求侧评估

### 5.1 文档自己的诚实声明（值得肯定）

`01_产品定义与交互.md` §1：

> 商业吸引力假设：持续跟踪多家公司的研究者，会为可靠的观点复核与记忆付费。**此项尚未经用户验证**，不把泛金融从业人数当作付费市场规模。

并给出验证方法：

> 让 5 位目标研究者使用自己的研报，完成一次首次核验、一次后续更新，观察他们是否愿意重复使用，以及是否比自己手工复核更快。

**这个假设至今零验证。** `15_架构决策与设计复核.md` 的苏格拉底式复核甚至自问了"用户会为它付费吗？"并诚实回答"目前无法仅凭架构证明"。

### 5.2 PM 判断：需求假设的三个真实风险

1. **"研究员愿意维护一个额外系统"本身是待验证的。** 产品的解法是"自动提取 + 少量确认"，方向对；但 T0 确认需要逐条校对观点表述、门槛、期间、口径——对 6 条观点这是 5–10 分钟的专注工作。**如果提取质量不够高，这个成本会超过手工笔记的成本，用户第二次就不会回来。** 而提取质量正是唯一没测过的东西。

2. **价值兑现周期长。** 产品的核心承诺是"下一期财报到来时，研究从旧状态继续"。A 股披露节奏意味着用户需要等 1–3 个月才能体验到第二次价值。**首次体验必须足够惊艳，否则等不到第二次。** 这把压力全部压在 T0→T1 的第一轮质量上。

3. **单人项目的运维承诺过重。** 设计文档要求：每日备份、RPO 24h / RTO 2h、恢复演练、结构化日志、指标监控、OIDC。这些对企业产品是基线，对个人项目是负担。**建议明确降级为"本地单机 + Markdown 可 Git 备份"，并把这条当作产品卖点（数据主权）而非缺陷。**

### 5.3 性价比最高的一步被搁置了

`officialFilingProvider.ts`（226 行，死代码）**已经实现了真实的 CNINFO 公告查询**：真实的 `POST http://www.cninfo.com.cn/new/hisAnnouncement/query`、真实的 category 参数、标题解析成 `ANNUAL/HALF_YEAR/Q1/Q3`、过滤"摘要"与"提示性公告"、识别"更正/修订"。

设计文档 P0-03 是"自动找到财报"，`15_架构决策与设计复核.md` 也自问"用户真的愿意先花时间维护一个复杂的观点库吗？"并回答"不能假定愿意。所以观点自动提取、公司自动识别、**财报自动获取是 P0**"。

**代码写了，没接线。** 接上就能把"用户手动找财报 + 手填期间口径"变成"系统提出候选 + 用户点选"，同时顺带解决 §4.9（期间由公告元数据带出，不再靠用户手填）。

⚠️ **但必须先修一个隐患**：它的兜底逻辑是**静默回退**到硬编码 fixture（圣邦 300661 / 汇顶 603160 的真实 URL），只在返回值里带 `source: "OFFLINE_BUNDLE"`。这违反文档自己定的原则——

> "截至今天没有新财报"和"这次没查成功"是两个不同结果。

接线时必须把回退改成**显式告知用户**，否则用户会以为系统查到了 2025 年报，实际读的是硬编码样例。

## 7. 战略判断

### 7.1 这个产品的真实完成度

| 维度 | 完成度 | 依据 |
|---|---|---|
| 产品思考 / 领域理解 | **90%** | 状态语义、口径检查、原因分层、证据门禁——都是真专业 |
| 设计文档 | **95%** | 罕见的高质量，含自我批评与边界声明 |
| 主链路实现（T0→T1→T2 骨架） | **~55%** | 同步可跑通，但无异步/进度/取消/幂等/分页 |
| API 契约 | **45%** | 15/33 路径 |
| 证据可追溯 | **~40%** | 页码+原文真，坐标假，无 PDF 渲染 |
| 工程收口（质量门/卫生/部署） | **~25%** | lint 红、5 测试失败、demo 污染、部署契约不符 |
| **真实验证** | **0%** | 从未带 Key 跑通过一次完整两轮 |

### 7.2 最大风险不是功能不够，而是核心假设零验证

这个项目最危险的地方，不是缺 18 个 API 或缺 PDF 渲染——这些都是可枚举、可排期的工程量。

**真正的风险是：没有人知道 Ling-3.0-flash-Fin 面对一份真实中文研报，能不能拆出研究员认可的观点。**

如果提取质量高 → 产品成立，剩下的都是工程。
如果提取质量低 → 用户需要在 T0 手工重写大部分观点，那么"不用手写 thesis"这个核心解法失效，产品退化成"一个带版本管理的投研笔记本"——价值大幅下降。

**而这个分叉点，只需要 1 份真实研报 + 1 个 Key + 半天时间就能测出来。** 项目已经投入了 19,000 行 TypeScript 和 2,900 行设计文档，却没有做这个半天成本的验证。

### 7.3 建议的下一步：纵向打穿一个案例，而非横向加功能

不要接 18 个缺失 API，不要做 PDF.js，不要迁 Postgres。

**做这一件事**：
