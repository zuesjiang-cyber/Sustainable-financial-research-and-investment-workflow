# 03 端到端工作流与状态机

## 1. 首次上传

1. `POST /v1/uploads` 接收 PDF 和角色 `THESIS_SOURCE`；流式写临时文件，校验 PDF 与大小，计算 SHA-256，移动到持久存储，落 Document。响应返回上传与文件 ID。
2. `POST /v1/runs` 传 `kind=INITIAL_REPORT`、上传 ID、幂等键。事务建立暂未绑定公司的项目、run、job，立即返回 202。
3. Worker 解析研报，识别公司、研报日期、提取范围。高确定性匹配公司后继续；有歧义则写 `WAITING_USER/COMPANY_SELECTION`，前端展示候选。
4. 提取观点，存原文及标准。此时用户已经能看到原观点，即使后面抓财报还在运行。
5. 按冻结的 `asOf` 发现正式财报，下载并解析最新报告及比较资料，落事实和来源。
6. Agent 逐观点规划与补查，生成判断、差距、原因、下一问题，计算相对初始观点的更新。
7. 写持久化 draft，run 进入 `AWAITING_REVIEW`。前端读取结果，不要求连接始终在线。
8. 用户可修改并重新核验部分观点，最后确认 draft。事务写状态 v1，run 变为 `COMPLETED`。

首次草稿中分别保留 `originalThesis` 与 `proposedCurrentAssessment`。第一次保存也不能让用户失去“研报最初怎么说”的基线。

## 2. 后续更新

手动「检查最新财报」创建 `REFRESH_FILINGS` run，基准为最近已确认版本。自动检查也是同一个业务入口，只是触发者不同。

公告目录相同且无修订文件：写检查时间和 `NO_CHANGE`，结束 run；不调用模型、不生成空版本。发现新报告或同名更正文件：冻结新资料包，复用旧文件解析和可比事实，重新评估受影响观点。报告未涉及的观点沿用状态但明确“本次无新增证据”，不能假装重新验证。

用户在已有项目上传新研报，创建 `ADD_REPORT` run：先按公司、指标/命题、时间范围和原意生成观点对齐建议（沿用、修订、新增）。只有确认后更新 active revisions；旧研报观点和历史仍能回看。新的财报仅改变 assessment，不改变原始观点文本。

## 3. Run 状态与阶段

| 状态 | 意义 | 后续 |
|---|---|---|
| `QUEUED` | 已持久入队 | Worker 领取后 RUNNING |
| `RUNNING` | 正在执行某阶段 | 下一阶段、等待用户、待审或失败 |
| `WAITING_USER` | 需公司/日期确认或补充关键材料 | 交互提交后重新入队继续 |
| `AWAITING_REVIEW` | 草稿完整，等待用户保存 | 重新核验，或确认完成 |
| `COMPLETED` | 已确认或无新资料 | 终态；再次研究新建 run |
| `FAILED` | 当前尝试不可继续 | 可恢复错误允许 retry |
| `CANCELLED` | 用户取消 | 保留已完成来源，不写状态 |
| `SUPERSEDED` | 同项目基准已改变 | 基于最新版本创建重算 run |

阶段顺序：`PARSE_REPORT → IDENTIFY_COMPANY → EXTRACT_THESES → DISCOVER_FILINGS → EXTRACT_FACTS → VERIFY → BUILD_DIFF`。刷新不执行前三项；新增研报额外执行观点对齐。每个阶段输出有版本化 schema 和内容哈希，成功后事务写检查点与事件。

WAITING_USER 是正常交互，不等于运行失败。AWAITING_REVIEW 的 draft 长期持久保存，不设“一小时过期即丢失”。

## 4. 持久执行

- jobs 每 2 秒领取一次就绪任务；租约 90 秒，20 秒心跳。长解析子进程由父 Worker 续租。
- 同一项目最多一个活动 run（QUEUED/RUNNING/WAITING_USER/AWAITING_REVIEW）；防止连续点击产生互相覆盖的草稿。已有草稿可继续审核、取消或重算。
- API 写 run 与 job 同事务。Worker 阶段产物落库后才推进 `checkpoint`。
- Worker 重启或失去租约：新 Worker 从最近完整检查点恢复。每次写检查点同时检查 lease token，旧 Worker 的迟到结果不得提交。
- 外部调用是至少一次执行；阶段结果依赖唯一键去重，最终确认是原子且幂等应用，不声称外部模型“恰好调用一次”。
- 网络 429/临时 5xx 最多 3 次，指数退避并遵守 Retry-After；用户上传的坏 PDF 不做无效网络重试。某观点证据不足以 UNRESOLVED 完成，而不是整轮失败。
- 取消只中止后续工作与可终止的子进程；已经发送的模型请求可能仍计费，结果丢弃。run 在后台任务确认取消后进入终态。

## 5. 重新核验与确认

用户修改草稿的观点/标准：`PATCH draft` 使用 If-Match，draft revision 增加，相关 assessment 标记 stale。点击继续核验后同一 run 重入 VERIFY，仅处理受影响观点，冻结其新输入哈希。不能直接把旧核验结果配到新观点上。

确认事务：锁项目 → 检查 `baseStateVersion` 和 `draftRevision` → 检查所有接受观点有相匹配的 assessment → 写 thesis revisions/corrections → 写 update 与 snapshot → 推进 project.current_version → run COMPLETED。确认请求重复时返回同一 update/version。

状态有并发变化时返回 409，前端展示“研究已经更新，正在按最新版本重算”；通过 `rebase` 新建 run，保留原草稿与人工修改，重新分析冲突项，不自动覆盖。

rebase 事务先把旧活动 run 标为 SUPERSEDED，再创建新 run/job，避免单活动 run 约束阻止重算。失败 run 的 retry 若发现另一活动 run，则返回其 ID；不并行抢写同一项目。REVIEW_STATE 只用于已有确认版本的项目。开启定期检查也要求公司已明确且至少已确认 v1。

## 6. 定期检查

项目设置 `monitor.enabled`；用户选择开启后按 `Asia/Shanghai` 每天 09:00 检查一次（这是产品默认时间，不是法定披露时间假设）。调度器由 Worker 定期扫描 `next_check_at`，通过数据库唯一键保证同一项目同一天只生成一次检查任务。

检查器查询目录，比较已保存公告标识、修订标识和内容哈希。发现新材料且无活动 run 时建刷新 run；有活动 run 时只记录 `pending_source_change`，待其结束后处理。无新材料仍更新“最后检查时间”。结果只在应用内展示更新徽标，不引入额外邮件/消息基础设施。

## 7. 进度事件

SSE 读取持久化 run_events，id 为全局递增序号。浏览器重连带 Last-Event-ID；API 只返回当前工作区和 run 的后续事件。事件通知状态变化与简短摘要，完整结果通过 GET run/draft 获取。

前端显示真实阶段、已完成观点数和运行耗时，不用虚假的平滑百分比或编造剩余秒数。SSE 断开自动改为每 3 秒查询快照，任务不会因页面关闭而取消。
