# 10 前端实现设计

## 1. 信息架构

只保留两个主页面：`/` 我的研究、`/projects/:id` 公司研究。`?run=` 恢复正在分析的草稿，`?version=` 回看历史。原“连续研究/单次测试”的模式切换退出主导航。

首页先展示一个上传区域和已有研究列表。用户点击已有公司，回到其当前研究；不先展示数据看板、指标面板、Agent 控制台。

## 2. 研究页线框

```text
公司名称                         [上传新研报] [检查最新财报]
覆盖：2026 半年报 · 已确认 v2 · 上次检查时间

[本次变化 3]  [全部观点 7]                 [历史]
---------------------------------------------------------
观点：高端产品占比提升将改善盈利能力           部分支持
最新事实：毛利率 29%，同比 +3 个百分点 [来源]
当前判断：利润率改善，但产品结构数据尚未披露。
下一步：查看下一期分产品收入占比。
[展开依据与原观点]                    [调整]
---------------------------------------------------------
                    [保存本次研究]  （仅草稿态显示）
```

“全部观点”与“本次变化”是同一列表的筛选，不是两个独立工作台。运行阶段用上传页/页头中的进度区替代结果列表，已经完成的观点可渐进显示。

## 3. 组件拆分

| 组件 | 职责 |
|---|---|
| ResearchHome | 上传入口、项目卡片、最近更新 |
| ReportUpload | 单文件拖放、文件校验、实际上传进度 |
| RunProgress | 阶段、已完成数量、交互暂停、重试 |
| CompanyResolution | 只有必要时展示的候选公司选择 |
| ProjectHeader | 主体、覆盖日期、版本、两个常用动作 |
| ThesisList / ThesisCard | 观点与新旧差异，默认紧凑展示 |
| ThesisDetails | 原句、标准来源、子条件、事实和原因层次 |
| ThesisEditSheet | 修改观点/标准/用户判断；标记需重算 |
| EvidencePanel | PDF 原页/文字来源与高亮 |
| ResearchHistory | 版本列表和选中版本；只读历史 |
| ConfirmBar | 保存本次研究、草稿失效提示 |

资料清单和运行过程放在研究页“详情”入口。Memory 是后台能力；前台最多有一个“研究偏好”轻表单，不做 Memory 数据库浏览器。

## 4. 服务端状态

`useProject(projectId)`、`useRun(runId)`、`useDraft(runId)`、`useRunEvents(runId)` 四个 hooks，内部共享 fetch client、AbortController、错误转换。不新增 Redux 等全局状态库。

URL 持有 project/run/version；后端保存任务、草稿和已确认研究。React local state 只存展开卡片、输入中的编辑和当前证据。组件卸载后中止读取请求，不取消后台任务。

PATCH 成功后以服务器返回的 revision 替换草稿；不乐观地把系统结果改成已经保存。发生 revision 冲突时保留用户尚未提交的文本并展示最新差异，不能丢输入。

## 5. 引用展示

点击 `[来源]` 打开侧栏，不跳走当前观点。默认显示 PDF 实际页与高亮；侧栏上方列出文件名、报告期间、披露日和引用原句。多证据可在侧栏顺序切换。

PDF.js 渲染页面，overlay 根据 normalized bbox 与 viewport scale/rotation 计算坐标；同一个 span 跨行/多页时使用多个 regions。缩放、旋转、翻页后重新计算。页码 UI 明确“PDF 第 N 页（报告页码 X）”。[PDF.js API](https://mozilla.github.io/pdf.js/api/)

旧文本来源显示原文高亮，不假装存在 PDF。OCR 低质量提示出现在引用旁，用户可比较页面图像。

## 6. 状态与文案

支持使用绿色、部分支持使用蓝色/中性色、削弱使用橙色、待验证使用灰色，同时保留文字与图标，不能只靠颜色。避免把所有不确定情况染成红色报错。

运行展示“正在拆分研报观点”“正在查找截至某日的最新财报”“已完成 3/6 条观点”；不要展示模型 token、工具 JSON 或模糊的“Agent 思考中”作为唯一进度。

核验结果不用统一的 92% 置信度美化精度。显示实质状态、原因、期限和证据质量就足够。

## 7. 交互完成要求

键盘可操作上传、主按钮和侧栏；焦点回到来源触发处；窄屏 PDF 侧栏变全屏面板。页面 skeleton 不遮盖已经得到的结果；无观点时说明原因并允许补充，而不是显示空表。

桌面 1440×900 和普通笔记本 1280×800 都能在首屏看到至少一个完整观点组；手机提供阅读、上传和确认的基本布局，但桌面投研是主验收环境。

## 8. 与现有 UI 的关系

保留已经有价值的证据侧栏、观点编辑和版本信息；将现有 NewProjectModal 从必经入口移除，改为上传后自动建项目。NewMaterialModal 的文本粘贴改为“补充材料”的次级入口。single_test 和 demoReplay 只在开发路由出现，真实用户首页不展示模式选择。

前端验收不是“删掉几个按钮”而是：首次用户无须理解 thesis/claim/tool，也不必手工录入观点就能走通真实流程。
