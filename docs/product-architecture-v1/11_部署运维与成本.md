# 11 部署、运维与成本

## 1. 部署形态

本地和云端使用同一应用：反向代理 → API（提供 React 构建静态文件）+ Node Worker + PostgreSQL。API/Worker 可以用同一镜像不同命令，Worker 镜像包含 Python 解析环境、Docling 模型资源和 Playwright Chromium。

默认单机 Docker Compose，文档和数据库使用独立持久卷。云端需要外部持久存储时替换 StorageAdapter 为 S3，不改变文档 ID 或研究契约。预先在构建/部署阶段下载所需解析模型，避免用户第一次上传才临时下载大模型。

起始资源预算：4 vCPU / 8 GB RAM / 40 GB 可扩展磁盘；单个重型解析并发 1、模型任务并发 2。**这是待测的起始配置，不是 Docling 的既定性能或部署容量承诺**。扫描长报表的峰值内存与耗时以实际资料测量后调整。

## 2. 环境配置

| 配置 | 内容 |
|---|---|
| APP_ORIGIN、PORT、AUTH_MODE | 同源地址、端口、local/oidc |
| DATABASE_URL | PostgreSQL 连接，API 与 Worker 相同实例 |
| STORAGE_DRIVER、STORAGE_ROOT | local 默认；S3 时另配 bucket/endpoint/region/凭据 |
| MODEL_BASE_URL、MODEL_API_KEY、MODEL_ID | Ling 的服务端调用配置 |
| MODEL_INPUT_PRICE_PER_M、MODEL_OUTPUT_PRICE_PER_M | 实际合同/路由单价，可未知；未知成本展示为未知 |
| OIDC_ISSUER、OIDC_CLIENT_ID、OIDC_CLIENT_SECRET | 云端登录提供方 |
| SESSION_SECRET | 足够随机的服务端 session 配置密钥 |
| PARSER_PYTHON、PARSER_PROFILE | 固定解析环境与模型路径 |
| WORKER_CONCURRENCY、PARSER_CONCURRENCY | 单机负载上限 |
| RUN_MAX_INPUT_TOKENS、RUN_MAX_OUTPUT_TOKENS、RUN_MAX_CALLS | 每轮预算 |
| UPLOAD_MAX_BYTES、PDF_MAX_PAGES | 上传与解析上限 |
| DISCLOSURE_PROVIDER、DISCLOSURE_REQUEST_INTERVAL_MS | 官方资料源和请求节奏 |

密钥只进服务端环境，不使用前端 VITE_* 注入模型 key。`.env.example` 只放占位说明，生产配置不进仓库。

## 3. 身份和文件访问

local 模式仅绑定 127.0.0.1，默认单用户；公开云端启用 OIDC Authorization Code + PKCE，state/nonce 校验，服务端保存 session，cookie 设置 HttpOnly/Secure/SameSite=Lax。openid-client 用于协议实现。[openid-client 官方项目](https://github.com/panva/openid-client)

云端每个用户一个私人 workspace；V1 不提供团队邀请、复杂角色管理或计费后台。部署者在 OIDC 提供方限制可登录的账号。上传和财报下载校验文件类型、大小、重定向域名与实际内容；服务器不会按任意模型给定地址读取本机文件或内网资源。

## 4. 构建和启动契约

未来实现需提供：`npm run dev`、`npm run worker:dev`、`npm run build`、`npm run db:migrate`、`npm run test:contract`、`npm run test:e2e`、`npm run eval:real`、`docker compose up --build`。这些是交付要求，**当前仓库并非已存在全部命令**。

依赖版本用 npm lockfile、Python lockfile 和镜像 digest 固定。数据库迁移在部署阶段执行一次，API ready 检查 schema version；每个 Worker 启动不自行重复修改 schema。

## 5. 最低运维能力

- 结构化日志：requestId/runId/projectId/phase、时长和错误码；避免记录全文与密钥。
- 指标：队列等待、解析成功率/页面数、官方获取成功率、模型调用/重试、token、每轮成本、UNRESOLVED 原因、确认率。
- 健康：API liveness/readiness、Worker heartbeat、模型配置检测；外部供应商临时故障不让整个应用首页不可用。
- 备份：每日 PostgreSQL 备份与文件卷增量备份到独立位置；保留至少 7 份日备份，按资源调整。目标 RPO 24 小时、RTO 2 小时，交付前演练恢复一次。
- 发布：先备份、迁移、启新镜像、验证健康与真实最小链路；应用回退只能配兼容 schema，破坏性迁移另做数据迁移方案。

## 6. 成本模型

```text
单轮模型成本 = Σ(inputTokens × 输入单价/1,000,000
                 + outputTokens × 输出单价/1,000,000)
单轮增量总成本 = 模型成本 + 按次资料/OCR成本 + 文件流量成本
月成本 = 固定主机与存储 + 各轮增量成本 + 备份费用
```

示例仅用于预算计算：假设输入 80k、输出 8k，输入 ¥2/百万、输出 ¥8/百万，则模型成本 ¥0.224。**这些是假设单价，不是 Ling 当前报价。** 单轮预算中提取研报、语义复核和失败重试都需要计入，不能只计最终摘要调用。

控制成本的实现顺序：哈希复用文件与解析 → 自动刷新无新披露时不调模型 → 只提取观点相关事实 → 批量共用基础事实 → 差量核验受影响观点 → 最后再优化提示词长度。

目标体验预算：文本型中等报告在普通网络上首次 2–5 分钟、已缓存后更新 1–2 分钟；扫描大文件可更久。作为测量目标写入验收报告，不提前宣传为已达到的性能。

## 7. 运行模式

真实模式必须走用户文件、真实解析、官方资料 provider、真实模型。回放模式只供 UI 开发和稳定演示预览，显示明显标签，数据 isSynthetic=true，不能写入真实项目或混入真实评测。模型不可用时展示可重试状态，不自动切换回放假装成功。
