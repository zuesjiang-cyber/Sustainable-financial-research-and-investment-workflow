# 08 数据模型与数据库

参考定义见 [domain.ts](contracts/domain.ts) 和 [schema.sql](contracts/schema.sql)。DDL 是成品设计基线，本次不对当前 SQLite 执行迁移。

## 1. 数据关系

```text
Workspace → Project → Thesis → ThesisRevision
                  → Run → Draft → ResearchUpdate → ResearchState(version)
                  → Questions / UserCorrections
Workspace → Document → DocumentParse → EvidenceSpan → Fact → Calculation
                          ↑                 ↑            ↑
                    Run source pack ───── Assessment 引用
Run → Checkpoints / Jobs / Events / ModelCalls
```

company 是标准主体目录；project 是用户对该主体的研究空间。上传时 company 可暂未识别，识别成功后绑定。不同用户的同公司研究不共享观点和私人研报。

## 2. 表职责

| 表 | 存储与关键约束 |
|---|---|
| workspaces、users、memberships、sessions | 云端私有工作区与 session；本地模式使用固定本地身份 |
| companies | exchange+security_code 唯一，官方主体标识和别名 |
| projects | 工作区、公司、当前版本、monitor 配置、归档状态 |
| documents | 上传/官方文件元数据、角色、SHA、storage key、披露与报告期 |
| document_parses | parser/version/options hash、结构化产物位置、质量 |
| evidence_spans | 原句、页码、bbox、表格位置、提取质量 |
| facts | 核心维度列用于过滤，完整 Fact JSON 用于回放 |
| calculations | 公式版本、操作数、结果、单位、检查结果 |
| theses、thesis_revisions | 长期 ID 与不可变语义版本 |
| runs、run_documents | 冻结时点、基准、资料包、阶段、来源角色 |
| run_checkpoints、jobs、run_events | 可恢复阶段、工作租约、可重连进度 |
| drafts | 持久草稿、revision、内容 hash、需重算观点 |
| research_updates、research_states | 确认记录、不可变快照，项目版本唯一 |
| user_corrections、research_questions | 可查询当前修正/问题；变化同时保留在 update |
| source_checks、model_calls | 新披露检查记录、模型耗时与使用量 |
| idempotency_keys、exports | API 幂等结果、异步可下载导出 |

JSONB 用于版本化业务载荷，Zod 在写入前校验。用于索引、过滤、并发的字段另列，不能只靠一大块 project JSON 处理所有关系。

## 3. 标识与数值

业务 ID 使用服务端生成的 UUID；浏览器不根据数组位置创建 thesis ID。财务值存 PostgreSQL numeric 或 JSON decimal string，对外均为字符串，前端不能用 JS 浮点数做正式核验。版本号为整数，从 0（尚未确认）开始。

所有应用时间为 timestamptz/ISO UTC；财务期间为 date，显示时区为 Asia/Shanghai。`publishedAt` 可未知但未知时不得宣称已满足历史 asOf；用户补充确认另存 provenance。

## 4. 工作区隔离

所有私人实体含 workspace_id；引用尽量用 `(workspace_id,id)` 复合外键，防止跨工作区串联。Repo 接口必须传显式 WorkspaceContext；无 owner context 的查询不对外暴露。

文件读取、SSE、导出和后台任务同样校验工作区，不只有项目详情鉴权。API 不信任客户端传的 workspace_id，用已登录 session 确定。模型调用只包含其 run 的允许文档。

## 5. 事务与一致性

确认 draft 时以项目行 `SELECT FOR UPDATE` 串行化，校验基准版本与草稿 revision；写 update、snapshot、thesis revisions、修正与问题，最后推进项目指针。唯一约束 `(project_id,version)`、`(run_id)` 的 update 和 idempotency key 保证重复确认返回同一结果。

网络与模型调用不放在长数据库事务里。先持久阶段输入，事务外调用，短事务内检查租约 token 和输入 hash 再写结果。已过期 Worker 的结果不接纳。

## 6. 队列领取与恢复

```sql
WITH picked AS (
  SELECT id FROM jobs
  WHERE status = 'QUEUED' AND available_at <= now()
  ORDER BY priority DESC, created_at, id
  FOR UPDATE SKIP LOCKED LIMIT 1
)
UPDATE jobs j SET status='RUNNING', lease_owner=$1,
  lease_token=$2, lease_until=now()+interval '90 seconds', attempts=attempts+1
FROM picked WHERE j.id=picked.id RETURNING j.*;
```

心跳更新条件包含 id+lease_token。回收器把过期租约且未超过重试次数的 job 重新排队，run 保持检查点。重试次数是 job 尝试数，模型单次请求重试另记，避免误以为只计费一次。

## 7. 索引与检索

- projects(workspace, updated_at)；documents(workspace, sha256)；runs(project, created_at)。
- facts(company, metric, period_end, basis, scope)，加 segment/性质过滤。
- evidence_spans(parse_id,page_number)，按 document 查询证据。
- run_events(run_id,id)，SSE 游标查询。
- jobs(status,available_at,priority)，并限制 RUNNING 的租约扫描。
- 观点规模较小时在 Worker 构建当前文档包 BM25 索引，索引产物绑定 parser/sourcePack hash；无需先建独立搜索服务。

## 8. SQLite 迁移

先复制旧数据库和完整原始文件备份，读取当前实际 schema，而不是假定仓库 HEAD 数据结构。导入到新库：projects→documents→theses→updates/questions，保留旧 ID 到新 UUID 的映射表（迁移产物 JSON）。

旧文本材料缺 PDF 来源时标记 `LEGACY_TEXT`，来源可查看原文本，不伪造 PDF 页码；旧 demo 数据明确 `isSynthetic=true`。历史状态尽量原样导入 `legacyPayload` 并提供旧版展示；只有完成规范化的字段进入新的自动核验链路。

迁移验收：项目/观点/更新/问题数对齐，随机检查用户修正与版本，导出前后比对。成功切换后旧库只读留存；新旧数据库不双写。现有脏工作区与用户数据不在迁移脚本中被清理。

## 9. 生命周期与导出

项目归档不会删除证据。V1 提供归档和导出，不额外建设自动删除生命周期。导出 ZIP 包含 manifest、研究 JSON、可读 Markdown、引用清单；勾选包含原 PDF 时只导出该用户有权取得的已存文件。迁移导入由受控脚本完成；P0 不额外建立跨版本通用导入平台。
