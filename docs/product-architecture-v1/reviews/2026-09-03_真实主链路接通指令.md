# 发给开发 Agent：接通 FinTrust 的真实研究主链路

请直接在现有项目上继续实现，不再重写 PRD 或增加技术展示页面。保留已有架构和模块，完成下面这条真正运行的流程：

> 真实研报 PDF → 自动提取观点 → 取得官方财报原件 → 提取事实并核验 → 用户确认并持久保存 → 新一期财报更新同一组观点。

先阅读 `docs/product-architecture-v1/reviews/2026-09-03_开发完成验收.md`。当前新首页是固定回放，后端模块没有接入产品入口；34 项测试通过并不代表真实端到端完成。

## 第一阶段：一份真实研报能跑到研究草稿

1. 修改 `ReportUploadView`，发送实际 File 内容至 `POST /v1/uploads`。保存文件、hash 和 document 记录，返回 documentId。接口字段按已有 OpenAPI，不另造平行契约。
2. 在 `server.ts` / `app.ts` 接入 V1 路由；`POST /v1/runs` 创建持久任务。启动 ResearchWorker，注册真实的解析和 RUN 处理器。前端读取 run 状态/事件，不再用延时动画制造已完成步骤。
3. 将 `PdfParserClient → ThesisExtractor → OfficialFilingProvider → FactExtractor → ResearchAgent → draft repository` 串联，补齐其中缺失的文件下载与数据转换。沿用现有 `researchModel` 模型传输层，按项目配置使用模型，不另起供应商接入工程。
4. 财报查询以识别出的公司和本轮 asOf 为准，下载正式报告及必要对比期报告。原件入 StorageAdapter，记录公告时间、报告期间、修订关系和 hash。离线样例只作为明确标注的预览与回归输入。
5. `ReportFirstContainer` 改为展示 API 返回的 draft、状态和 evidence，移走正式路径中的 `sampleSpans`、固定圣邦股份对象和假进度。样例可以保留在独立 demo 模式，但正常上传不能走该路径。

本阶段演示：上传真实研报，后台实际产生文件、解析结果、观点、财报文件、事实与 draft；页面显示与上传公司一致。若缺环境或测试材料，列出确切缺项，不用固定答案替代执行。

## 第二阶段：每个判断能解释清楚、查到原件

1. 复用并接通已有工具契约：`find_facts`、`search_evidence`、`read_evidence`、`request_disclosure`、`calculate_metric`、`submit_assessment`。Agent 根据观点决定还需什么证据，而不是固定执行几段模板。
2. 数值核验按公司、报告期间、比较期间、CAS 合并口径、币种、单位和分部匹配。比较运算覆盖条件中实际支持的操作符；趋势使用当前期与比较期，全年预测结合成熟度判断。计算用 Decimal，保存可解析的 calculation 记录和输入事实引用。
3. 取消无条件写入的管理层解释。先形成观测差距，再提取披露中的原因；原因没有被披露就保持缺失。模型提出的解释放入 hypotheses，写明仍需什么材料。纯数值事实的引用不能代替管理层因果原文。
4. 保留原因不足或无法量化的观点及其未解问题，不用现金流、毛利率模板代替所有观点。提取器中的年份、公司和核验门槛必须来自实际材料或明确的用户修正。
5. 证据侧栏加载原始 PDF，定位物理页与真实段落/单元格。修正解析坐标，表格事实保留表头、行名、期间及单位上下文；扫描材料按既定解析设计处理。保持页面简洁，坐标等技术字段不占主展示区。

本阶段演示：任意一条核验结果都能从观点跳到事实、计算和原页；至少展示一个有证据的差距解释、一个未被证实的原因，以及一个尚未到期的预测。

## 第三阶段：保存一次，下一次沿着它继续研究

1. 将保存按钮接到 `POST /v1/runs/{id}/draft/confirm`，调用并实测已有 `DraftsRepo.confirmDraftToState` 事务。成功响应后才显示“已确认入库”。读取接口恢复当前项目、草稿和已确认状态。
2. 观点使用稳定 thesisId。修改观点文字或标准创建 revision，并对受影响观点重新核验；用户独立判断单独保存，清空判断也是有效修改。
3. “检查最新财报”实际查询新披露。发现新材料后，加载上一确认版状态和 UserCorrections，通过 ContextCompiler 进入新一轮；新 assessment、diff 与待解决问题基于真实材料生成。
4. 复用 DiffGenerator / StateManager，保留原研报、历史判断和用户修正。问题是否已回答需匹配问题及证据，不因为出现了年报或任意差距就统一标为已解决。
5. 前端只需要上传入口和研究工作台；已保存研究可重新打开，工作台呈现“原观点、最新事实、变化原因、我的判断、下一步关注”。无需新增 Memory 或 Agent 配置面板。

本阶段演示：保存 v1 → 刷新/重启仍可恢复 → 加入新一期财报 → 同一观点产生 v2 diff → 用户修正继续存在 → 能回看 v1 的证据。

## 交付时提供这些运行证据

1. 当前启动、迁移、Worker 与测试命令，以及已实测的运行环境。沿用既定 PostgreSQL 目标；不要宣称尚未验证的数据库兼容或部署成功。
2. 一份真实研报和对应财报的 documentId、runId、文件 hash、来源时间与一组实际核验结果。材料由用户提供时直接复用，无需重新搜集一套展示数据。
3. 一个真实保存后的 state v1，以及新财报触发的 state v2，展示稳定观点身份、人工修正和变化原因。
4. 用另一家未硬编码公司的材料重复主要流程，结果不得串公司。
5. 集成测试必须经过实际文件上传、HTTP API、持久仓储和 Worker；增加服务重启恢复检查。可复现的离线回归与真实联网/模型验收分别报告。
6. 加入两条针对性语义回归：无证据不能生成“管理层解释”；同口径现金流从 2 亿降到 1 亿不能支持“同比改善”。不要只断言字段存在或原因数组非空。
