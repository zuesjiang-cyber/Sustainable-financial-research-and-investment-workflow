# 15 架构决策与设计复核

## 1. 已选定的决策

| 决策 | 原因 | 代价与重新考虑条件 |
|---|---|---|
| 研报上传为唯一主入口 | 对齐研究者真实输入，消除手工建观点负担 | 提取质量成为产品核心，必须有真实标注 |
| 观点而非聊天作为长期对象 | 后续能明确回答“什么变了” | 需要稳定 ID、版本和对齐算法 |
| 一个 ResearchAgent + 可测工具 | 自主补查与财务严谨性可以同时实现 | 需要明确阶段与停止条件，不靠框架替代设计 |
| PostgreSQL 持久状态和队列 | 页面关闭/Worker 重启后继续，避免内存草稿丢失 | 引入一个服务；若仅做离线脚本才值得用 SQLite 简化 |
| Docling 子进程 | 保留页面/表格结构，适配文本和扫描材料 | CPU/内存与中文质量要实测；接口可换解析器 |
| 结构化事实 + 本地 BM25 | 单公司研究规模适合，数值不能只靠语义相似 | 大文档集检索失败有证据后再评估向量混合检索 |
| Agent 自动分析、用户确认状态 | 用户判断有归属，历史可靠 | 多一次保存动作；用一键整轮确认减轻负担 |
| 私人工作区 | 符合个人展示与研究资料使用方式 | 先不做多团队商业化运营能力 |

## 2. 苏格拉底式产品复核

**如果只是上传 PDF 后总结，用通用聊天产品不就行了吗？**

是。因此摘要不是完成条件。产品必须自动对齐研报旧观点与正式财报新事实，保留来源、期限、用户修正和第二轮变化。验收第三段演示专门证明连续性，而不是堆一个聊天框。

**用户真的愿意先花时间维护一个复杂的观点库吗？**

不能假定愿意。所以观点自动提取、公司自动识别、财报自动获取是 P0；用户的工作是少量修正与确认。首页不暴露 schema 或 Agent 配置。

**既然不能充分证明因果，原因分析还有价值吗？**

有价值，但价值在于把可观察差距、公司披露解释和待验证假说拆清。研究者知道下一步缺什么，比拿到一段混合真假原因的漂亮总结更有用。

**自动抓最新财报做不到怎么办？**

补充上传保证用户能继续，但不作为最终自动能力的替身。早期先实测沪深各一个主体的官方获取，再铺其余代码；若公开源不稳定，选合规、可负担的授权 provider，并公开说明凭据与费用。不能到最后才发现最重要的承诺无法运行。

**Memory 会不会只是存几段摘要的包装？**

如果下一轮不使用原观点、修正和待解问题，就是包装。本方案通过状态版本、context compiler 和两轮验收检查它是否真正改变后续行为。

**这么多后台结构会不会把前台重新做复杂？**

不必。原文件、事实、任务、模型轨迹留在服务层，前台只围绕“原观点—事实—判断—变化”。接口将计算结果聚合为观点卡，不让用户自己拼表。

**为什么这是个人可以做的产品，而不是一个大机构平台？**

限制在中文沪深公司研究、单一主路径、单体部署、固定工具、一个核心模型，复用现有版本与计算代码。工程难点集中在 PDF、官方来源、核验和连续性，避免分散到行情终端、交易执行和企业协作。

**如何展示金融 × AI 的竞争力？**

展示真实判断：累计/单季、归母/合并、预测期限、百分点、因果边界；同时展示 Agent 根据证据缺口补查、确定性计算、可回溯状态和用户修正。这些能从代码和演示中证实，不需要夸大为自动投资经理。

**用户会为它付费吗？**

目前无法仅凭架构证明。关键观察是：他们是否带自己的报告来、是否认可核验省时、是否在下一期披露后回来。优先做五个目标用户的两轮使用测试，不用虚构市场规模替代需求证据。

## 3. 与前期方向的关系

延续前期关注的持续研究与 Memory 思路，但把实现入口纠正为“研报→观点”，而不是“用户先建观点再分析新材料”。当前文档不是新一轮 LongAlpha 竞品研究，未核实其当前功能，因此不把推测的竞品功能作为事实或技术依赖。

产品差异不需要全面碾压竞品。当前值得打磨的三个点是：研报观点自动结构化、金融口径明确的事实核验、可被用户修正并持续使用的研究状态。这些是本产品设计选择，不是假定别人没有。

## 4. 仍需实测的假设

官方公告获取成功率；中文扫描/跨页财务表的解析质量；Ling 在固定 schema 和中文核验上的正确率/成本；用户是否认同观点拆分粒度；第二轮相比手工流程能节省多少时间。

它们都有明确对应任务和验收资料，不是无限扩展的风险清单。用一个真实主案例尽早检验，再决定优化哪一处。
