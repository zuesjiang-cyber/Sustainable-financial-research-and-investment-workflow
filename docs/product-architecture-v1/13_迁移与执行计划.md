# 13 迁移与执行计划

## 1. 执行方式

本目录是完整终态设计；下面九项是实现它的工作包，不是把产品再缩成仅做某一轮 demo。具体任务在 [CCPM Epic](../../.claude/epics/report-first-product/epic.md)。架构负责人审契约与闭环，Luna max 负责代码实现与对应测试。

| 任务 | 交付物 | 依赖 |
|---|---|---|
| 001 领域契约与持久运行底座 | shared schemas、PostgreSQL、repos、jobs、checkpoint、StorageAdapter | 无 |
| 002 研报上传与观点提取 | 真实 PDF 解析、页码、公司识别、原子观点 | 001 |
| 003 官方财报获取与事实 | provider、资料包、事实标准化、确定性指标 | 001 |
| 004 Agent 核验与解释 | 工具循环、三层校验、期限、差距/原因/问题 | 002、003 |
| 005 持续状态与研究记忆 | 确认事务、修正、历史、第二轮 diff | 004 |
| 006 简洁前端与证据阅读 | 上传/进度/结果/编辑/PDF/历史 | 001；最终联调需 004、005 |
| 007 新披露检查与完整 API | scheduler、缺失资料交互、导出、端到端 API | 005 |
| 008 私有部署与迁移 | OIDC、Compose、旧数据迁移、备份恢复 | 001；验收需 005、007 |
| 009 真实资料验收与交付 | 真实两轮闭环、质量/成本记录、操作说明 | 002–008 |

002、003、006 可在 001 契约稳定后并行，006 先用契约样例开发；不要让三个 Agent 同时改 App、app.ts 或 shared types。集成负责人管理共享契约变更。

## 2. 开发顺序中的可展示节点

节点 A：用户上传自己的研报，能看到真实自动提取的观点和原页。节点 B：自动获取财报并逐条核验，有真实来源。节点 C：页面简洁且可确认，第二期沿用同一研究状态。节点 D：私有环境部署、真实验收、恢复和导出完成。

这些节点用于尽早发现方向偏差，不代表 A/B 就已经交付完整 V1。优先把一家公司贯通，再扩大资料集；不先独立建设泛用文档平台和复杂操作后台。

## 3. 从现有系统迁移

1. 记录当前工作区、未提交改动和数据库副本，不能覆盖用户或已有 Agent 的工作。
2. 在当前仓库逐模块替换：先添加 v1 接口与新持久层，旧界面继续可运行作参考。
3. 新上传流程稳定后，首页切换为 report-first；旧手工 thesis 入口退出主要流程。
4. 迁移已有真实项目、修正、问题和历史；演示数据保留 synthetic 标记。
5. 新主流程完成后移除对内存 draft、SQL.js 写入和单次测试入口的运行依赖。可以保留旧文件与迁移读适配，不要求为“整洁”大规模删除代码。

## 4. 工作量估算

这是估算，不是对 Agent 编码速度的承诺：单名有经验开发者约 18–28 个有效工程日，资料与模型环境就绪、复用现有计算/版本逻辑的前提下。自动化编码可减少重复工作，但官方来源联调、中文表格质量和真实核验标注仍需时间。

主干实现大致 10–15 日，真实资料和部署收口约 5–8 日，外部源/解析问题预留 3–5 日。可以更早展示节点 A/B，但不能把整个终态架构压缩成“改几段 prompt 就完成”。首个实现任务需先验证官方获取和中文 PDF 两个外部不确定性，失败时调整适配器，不把缺功能改名为完成。

## 5. 给 Luna 的统一执行指令

> 在现有 fintrust-research 中实施 report-first-product，先读 docs/product-architecture-v1/00_README.md、01、02、03、06、07 和本次任务对应章节，再读 contracts 与 CCPM 任务。主路径是用户上传研报，自动提取观点，获取最新官方财报、拆事实、核验观点，并在后续更新中维护原观点与用户修正。不要让用户重新手写 thesis；不要把回放当真实完成。仅实现分配任务，遵守文件所有权，复用已有有效代码与测试。字段或接口需要改变时先向架构负责人说明受影响契约。每次交付报告修改文件、实际运行的测试、真实演示路径、未完成项；不要把未执行的检查写成通过。保留当前脏工作区和用户数据库。

每个具体任务额外给出可编辑文件、接口输入输出、验收命令与依赖产物。Luna 的模型/推理档位按用户要求设为 `gpt-5.6-luna / max`；本轮只完成设计，不启动业务开发。

## 6. 架构负责人的验收问题

- 是否真的从上传 PDF 开始，而非预置 JSON？
- 事实来自哪些自动取得的正式财报，最新覆盖如何确定？
- 原研报目标、当前事实和用户判断是否分开？
- 数字/时间/因果判断能否解释并回到来源？
- 第二轮是否使用上次状态，还是重新做一个无关摘要？
- 页面是否让研究者看观点与变化，而不是理解系统内部结构？

任何任务“完成”都要能回答它相关的问题。验收集中在核心链路正确与可展示，不扩展为全面安全审计或无止境样式修整。
