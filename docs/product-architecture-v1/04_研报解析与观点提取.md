# 04 研报解析与观点提取

## 1. 输入和解析产物

主入口接受 PDF。设计初值：单文件最多 50 MB、500 页；部署可调整并用大报告实测。加密不可读文件提示上传解密副本；解析服务不会要求用户先转 TXT。TXT/Markdown 作为补充笔记，不取代 PDF 主链路。

Worker 通过参数数组启动 Python 子进程：`parser --input <local-path> --output-dir <run-dir> --profile research-report`。路径由 StorageAdapter 创建，不拼接 shell。子进程输出 JSONL 进度和最终 manifest；超时 15 分钟、内存限额、临时目录和文档 SHA 绑定。Cloud 模式先把对象下载到隔离的临时工作目录。

Docling 负责页面/段落/表格结构；文本稀少、乱码或图像覆盖页面启用 OCR，再保留解析质量。实际 OCR 引擎在 Python 锁文件中固定为支持中文的 RapidOCR 配置；开发启动先验证模型资源完整并预热。选择依据是文档结构和溯源能力，中文表格准确率必须由本项目测试资料证明。[Docling 项目](https://github.com/docling-project/docling)

规范化输出：

机器可校验结构见 [parser-manifest.schema.json](contracts/parser-manifest.schema.json)。blocks/tables 的 regions 在 Node 持久化时转为 EvidenceSpan IDs，业务引用使用这些 ID。

```text
document.json: schemaVersion, fileSha256, parserVersion, pages[], blocks[], tables[]
page: pageNumber(从1开始), printedLabel?, widthPt, heightPt, rotation
block: id, type, headingPath[], text, spans[]
table: id, caption, headers[], cells[], continuationOf?
cell: row, col, rowSpan, colSpan, text, bbox, pageNumber
span: documentId, parserVersion, pageNumber, bbox, quote, textHash, quality
```

`bbox=[x0,y0,x1,y1]` 统一为去旋转后页面左上角原点、0–1 归一化坐标；Docling 的坐标系与 PDF.js 视图坐标在适配层转换。实体、数字和引用永远使用 PDF 物理页码；报告印刷页码只作为附加标签。

## 2. 文本与表格处理

保留原始文本，另建检索标准化文本（空白统一、全半角统一、中文术语分词）。引用使用原文，不使用检索串。相似页眉页脚按跨页频率识别，排除于检索但不删原文件。

跨页表格通过标题、列头、连续行和页序合并；每个单元格仍指回原页。数值、单位、科目标签、列头、脚注分别保留，不能把一整页表拼成无法判断期间的一段文字。

低质量页面不自动产生确定事实；作为低置信候选展示原图/文本，后续核验标记来源读取不可靠。用户可补充更清晰文件；解析器升级后重解析产生新提取版本，原文件和旧版本不被覆盖。V1 不增加手工表格/OCR 编辑器。

## 3. 公司与时间识别

先读封面、标题、页眉、证券代码和报告发布日期。公司匹配使用证券代码+交易所字典，不仅使用中文简称。实体包含 canonical issuer ID、证券 ID、曾用名和上市地；这些来自官方目录同步或用户提供的种子目录。

匹配规则：明确代码且名称相符可自动选中；多个目标或代码/名称冲突则 WAITING_USER。行业报告允许用户选择一个主体，再仅提取与其有关的观点；不能把同业数据当目标公司事实。

日期优先报告明确发布日期，其次原文件元数据提示但需确认，不能用文件上传时间假定研报写作时间。`asOf` 是本轮信息截点，独立于研报日期。

## 4. 两步提取观点

**第一步：覆盖扫描。** 按标题切块，每块建议 4k–6k tokens，保留前后段、图表标题和页码。扫描投资要点、盈利预测、业务驱动、风险、正文关键假设，产出候选命题和原文 span IDs；不是只拿研报第一页摘要。

**第二步：原子化、分组和去重。** 每个命题聚焦一个可核验对象，记录与父论点的关系。例如“高端产品占比提升将带动明年毛利率超过 30%”拆成：

- 高端产品占比提升（经营趋势）；
- 明年毛利率超过 30%（期限明确的数值预测）；
- 产品结构改善驱动毛利率上升（因果关系）。

三者组成一个观点组。即使毛利率达到目标，也不能据此把产品结构与因果链全部标为支持。

## 5. 每条观点的契约

包含 stable thesis ID、group ID、原句及来源、忠实改写、命题类型、主体、业务分部、时间范围、原研报证据、核验条件、优先级、提取问题。

类型：`NUMERIC_FORECAST / DIRECTIONAL / CAUSAL / QUALITATIVE / HISTORICAL`。

核验标准的来源分别标记：

- `REPORT_EXPLICIT`：研报明确提出数值或条件；
- `SYSTEM_PROPOSED`：为含糊说法建议的可观测标准，前端显示“建议”；
- `USER_CONFIRMED`：用户确认/修订后的标准，保留前一版本。

“高速增长”不能偷偷改写成“增长 20%”。系统可以提议阈值，但未确认前仅按方向或相对历史比较，并以待明确标准解释局限。

## 6. 验证条件 AST

条件用结构化 AST，不保存可执行模型代码：

```json
{
  "kind": "COMPARE",
  "metric": "gross_margin",
  "op": "GTE",
  "target": "0.30",
  "unit": "RATIO",
  "period": {"start": "2026-01-01", "end": "2026-12-31", "basis": "YEAR"},
  "scope": "CONSOLIDATED",
  "origin": "REPORT_EXPLICIT"
}
```

支持 Compare、Trend、Semantic、All/Any；复合条件保留子条件身份。业务分部使用可空 segment；无法精确映射时产生澄清问题，而不是把公司整体指标代入分部指标。

## 7. 去重与观点身份

首次按主体、命题类型、指标/语义主题、期间、方向去重，引用汇总但保留所有原句。LLM 提出合并候选，程序检查主体和期间一致后合并。不同预测年份不是同一个数值目标。

后续研报对齐只提出建议：同一长期主题沿用 thesis ID，期限目标变化产生 revision；性质不同的新命题新建 ID。相关但独立的因果和结果命题不能仅靠向量相似度合并。

## 8. 产物校验

每条正式候选必须至少一个有效 source span，原句存在于本轮解析结果；模型不得返回自由编造的页码。数字、年份、单位从原文核对，任一缺失标记 extraction issue。

标题级“看好公司长期发展”可以作为观点组摘要，但需要拆出具体依据才进入核验列表。营销套话和投资评级单独保留为背景信息，不挤占主要核验结果。
